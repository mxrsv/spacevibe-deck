# Accounts MVP: Google sign-in and tiers

- **Started:** 2026-10-20
- **Status:** Approved by the owner on 2026-10-20, MVP scope. Implementation is in progress.
- **Baseline:** `main` at `f74328ff`.
- **Surfaces:**
  - **Electron main:** a new account service.
  - **Renderer:** an account control and a Settings → Account page.
  - **Supabase:** a migration under [`backend/supabase/`](../../backend/supabase/).
  - **Privacy notice:** a new dated version.
  - **Untouched:** the analytics Worker and the landing's feedback sign-in.

## Goal

A Deck user can sign in with Google and see the tier their account is on. Signing in is
optional: signed out, every feature works as it does today and Deck reads "No account". Deck is
free and open source, so there is no billing. The paid tier is a server-side value that nobody
holds yet. This is the smallest version that does that. Everything else waits in
[Later](#later-scale-path), and the account model is shaped so a future mobile app can sign
into the same account.

## Decisions (owner, 2026-10-20)

1. **Identity and tier only.** Settings sync and feedback attribution come later.
2. **Google sign-in, through Supabase Auth.**
3. **Reuse Deck's Supabase project** (`calkpkscykzmvyayfxih`), the one behind feedback. Account
   tables live beside the feedback tables, each with its own RLS.
4. **No charging.** Deck gates nothing on tier.
5. **MVP first, scale later.**

## Decisions taken in this spec (approved with it)

- **D1. Loopback callback.** Sign-in redirects to
  `http://127.0.0.1:<ephemeral port>/auth/callback` with PKCE, as RFC 8252 §7.3 recommends for
  native apps.
  - **Turned down:** a `deck://` URL scheme. It is a bundle-config fork: it needs
    electron-builder `protocols`, registry entries on unsigned Windows builds, registration in
    dev runs, and second-instance argv handling.
- **D2. `@supabase/supabase-js`, in the main process only.**
  - **Turned down:** hand-written `fetch` against GoTrue. It is smaller, but PKCE exchange and
    token refresh are security code that the official client already maintains.
  - **Shared with mobile:** a future mobile app would use the same SDK against the same tables.
  - **Bundle size does not matter:** the Electron framework dominates the installer.
- **D3. Tier values:** `free` and `pro`. A missing or unknown value reads as `free`.
- **D4. Two Google sign-in paths coexist on purpose.**
  - **Landing feedback** keeps Google Identity Services, verified by the Worker
    ([2026-10-08 spec](2026-10-08-feedback-sign-in-status-mail.md), decision 2).
  - **The app** uses Supabase Auth.
  - **Merging them later is a join, not a migration.** Google gives one account the same `sub`
    across OAuth clients, so the join is on `auth.identities.provider_id`.
- **D5. No remote avatar.** The renderer shows the account's initial and email, and gains no new
  network origin.

## Requirements

### Signed out

- **A1. Optional.** No feature, menu action or setting requires an account. Deck never prompts
  the user to sign in.
- **A2. "No account".**
  - **Rail control:** signed out, an account control in the rail's foot reads "No account" and
    opens Settings → Account. Top-tab mode has no rail, so there the page is reached through
    Settings only.
  - **One placement:** the MVP builds one placement, and the owner approves it from a
    screenshot. There is no specimen round.
  - **Signed in:** the same control shows the account's initial and its tier.
- **A3. Zero network.** Signed out, Deck sends no request to Supabase or Google. The supabase-js
  client is built only when a stored session exists or a sign-in starts.

### Sign in

- **A4. Flow.** "Sign in with Google" runs these steps in main:
  1. Start a one-shot HTTP listener on `127.0.0.1`, port 0.
  2. Ask supabase-js for the Google authorize URL, with PKCE, `redirectTo` set to the
     listener's callback, and `skipBrowserRedirect`.
  3. Open that URL with `shell.openExternal`.
  4. Accept only `GET /auth/callback`, and exchange its `code` once.
  5. Reply with a static page: "Signed in. You can close this tab and return to Deck."
  6. Close the listener.
- **A5. Bounded.**
  - **While signing in,** the button becomes Cancel.
  - **The listener closes** on success, on Cancel, on error, or after 5 minutes. When the flow
    did not succeed, Deck returns to signed out.
  - **No port stays bound** once the flow has ended.
- **A6. Errors.** A provider error in the callback, a failed exchange, or being offline ends
  signed out. Deck shows a one-line reason and does not retry.

### Session

- **A7. Tokens stay in main.** The renderer receives only a display state, never a token. The
  state is `signed-out`, `signing-in`, or `signed-in` with `{ email, name, plan }`.
- **A8. Encrypted at rest.**
  - **Storage:** the session persists in `userData/account.json`, encrypted with
    `safeStorage`.
  - **Encryption unavailable:** the session is kept in memory only. It is never written in
    plaintext.
- **A9. Unreadable file.** Deck treats a file it cannot read or decrypt as signed out.
  - **Kept until a sign-in:** nothing overwrites it except the next successful sign-in.
  - **Why replacing it is safe:** it holds only a credential that cannot be recovered, so the
    store write-lock rule does not apply.
  - **Sign out** deletes it.
- **A10. Refresh.** supabase-js refreshes tokens in main.
  - **Server rejects the refresh:** Deck signs out.
  - **Network failure:** Deck stays signed in.
- **A11. Sign out.**
  - **Local first:** Deck clears the local session, then revokes the refresh token, best effort.
  - **Offline:** sign-out still completes locally.
  - **Deletion failure:** if the credential cannot be removed, report that the saved account
    remains and may return on restart. Never silently claim durable logout; the sign-out
    operation remains safe to retry.
  - **Other data is never touched:** sign-out deletes only `account.json`. It never changes
    workspaces, settings, session restore or any other file.
- **A12. Every window agrees.** Main owns the state and broadcasts each change to every window.

### Tier

- **A13. The server owns the plan.** The migration creates `public.profiles`:

  ```sql
  id uuid primary key references auth.users on delete cascade,
  plan text not null default 'free' check (plan in ('free', 'pro')),
  created_at timestamptz not null default now()
  ```

  - **Row creation:** a `security definer` trigger, with a fixed `search_path`, creates the row
    when a row is inserted into `auth.users`.
  - **No desktop-only columns.**
- **A14. RLS.**
  - **Enabled** on `profiles`.
  - **Read own row only:** `authenticated` may `select` only its own row.
  - **No writes for clients:** no insert, update or delete policies, and those table privileges
    are revoked from `anon` and `authenticated`.
  - **Trigger function:** `EXECUTE` is revoked from `public, anon, authenticated`.
  - **Plan changes** are an owner action in Studio.
- **A15. Reading the plan.** Main reads `plan` after sign-in and once per launch. A failed read
  shows Free.
- **A16. No gating.** Deck displays the plan and nothing else.

### Privacy, security, docs

- **A17. Public key only.** One main-process config module holds the project URL and the
  publishable (anon) key.
  - **Test override:** unpackaged builds may override both, so tests can point at a stub.
  - **Service-role key:** it never enters the app or the repo.
  - **This is the project's first public key.** Shipping it lets anyone call PostgREST as
    `anon`, or as `authenticated` after signing in, across the whole project, feedback included.
  - **Existing objects already deny both roles:** `feedback_reports` revokes all from them, and
    both trigger functions in
    [`20261008000100_feedback.sql`](../../backend/supabase/migrations/20261008000100_feedback.sql)
    revoke `EXECUTE`. Every new object follows the same rule.
- **A18. Telemetry unchanged.** No account field enters the analytics payload or crash reports.
  The payload snapshot test passes without edits, and nothing calls `Sentry.setUser`.
- **A19. IPC.** The new channels are `account_state`, `account_sign_in`,
  `account_cancel_sign_in` and `account_sign_out`, plus the event `account:state-changed`.
  - **Contract test (R6):** all of them go in `scripts/electron-ipc-contract.test.ts`.
  - **Renderer access (R8):** through `src/host/account-host.ts`.
- **A20. Privacy notice.** A new dated notice under `marketing/public/privacy/<date>/` covers:
  - Google sign-in is optional, and Deck sends nothing when signed out;
  - what is stored: email, name, Google account ID, plan, and sign-in times;
  - Supabase is the processor, and Google is the identity provider;
  - how to erase an account: ask the owner.

  `/privacy` points at the new notice, and earlier notices stay.
- **A21. Docs.**
  - **[`backend/README.md`](../../backend/README.md)** gets an Accounts section covering the
    migration, provider setup, redirect allow-list, plan changes and erasure.
  - **`docs/internals/`** gets one paragraph on why the session stays in main.

## Acceptance criteria

- **Signed out:** a counting `fetch` injected into the account service records zero calls
  (A3).
- **Sign-in against a stubbed GoTrue** (unit tests with fake timers):
  - a code ends signed in with `free`;
  - a provider error ends signed out;
  - Cancel and the timeout both close the listener.
- **No token in the renderer:** the state payload shape is pinned by a test (A7).
- **Encryption unavailable:** `safeStorage` reports no encryption, and nothing is written.
- **RLS:**
  - A user reads only their own `profiles` row and cannot update `plan`.
  - `anon` reads nothing.
  - An authenticated user cannot read `feedback_reports`.
  - The checks run as a pgTAP test on the local stack. Without Docker, they run as a SQL role
    check against the linked project. Either way, the plan records which one ran.
- **Telemetry:** the analytics payload snapshot passes without edits.
- **E2E gate ([`test-deck-app`](../../.claude/skills/test-deck-app/SKILL.md)):** walk this flow
  against a stub auth server:
  1. "No account" shows;
  2. Settings → Account opens;
  3. sign in, with `openExternal` intercepted and the callback simulated;
  4. the initial and Free show;
  5. sign out;
  6. "No account" shows again.
- **Owner check, not a gate:** one real Google sign-in on macOS before release.

## Expected forks (authorized by approving this spec)

- **Runtime dependency:** `@supabase/supabase-js` (D2).
- **Main-process persistence and network calls:** `account.json` and the account service. These
  are not a PTY, window, tab or layout seam.

**Not forks:** no URL scheme, and no change to electron-builder, the updater, signing or the
version.

**Still stops the run:** any change to a DL invariant.

## Later (scale path)

Ordered by how often comparable terminal and agent apps put each item behind sign-in:

1. **Settings sync** across machines.
2. **Mobile companion app.** Specified on 2026-11-04 in
   [its own spec](2026-11-04-mobile-companion.md), which pairs by QR without an account. If an
   account gate is added later, the iOS app must offer in-app account deletion (App Store
   guideline 5.1.1(v)), which needs a Worker route that holds the service-role key.
3. **Paid features.**
   - **What they would be:** remote workspaces and team features, which are what comparable
     apps charge for.
   - **What it needs:** billing.
   - **What stays free:** anything that runs locally.
4. **Merging the landing's Google sign-in** into Supabase Auth (D4).
5. **More providers,** such as GitHub.
6. **Polish.**
   - **Specimen round** for the account placement.
   - **Avatar.**
   - **Offline plan cache.**
   - **A `docs/user/` sign-in page.**

  client.
  - **Redirect URI:** add `https://calkpkscykzmvyayfxih.supabase.co/auth/v1/callback`.
  - **Client secret:** create one.
  - **Consent screen:** name it "SpaceVibe Deck", with scopes `openid email profile` only.
- **Supabase → Authentication → Providers:**
  - **Google:** enable it, then paste the client ID and secret.
  - **Email and Phone:** disable both.
  - **Anonymous sign-ins:** confirm they are off.
  - **Why:** once the key is public, an open Email provider lets anyone create accounts.
- **Supabase → Authentication → URL Configuration:** add `http://127.0.0.1:*/auth/callback`.
  - **Unverified:** whether `*` matches a port. The plan's first task checks it. If it does not
    match, the fallback is a small fixed port range.
- **Migration:** run `db push` for the account migration before shipping.

## Delivery

backend and the UI to run in parallel, as two subagent lanes in their own worktrees:

1. **Contract first, on `main`:** the channel and event names in
   [`electron/ipc/channels.ts`](../../electron/ipc/channels.ts), and the renderer facade
   [`src/host/account-host.ts`](../../src/host/account-host.ts). Both lanes branch from that
   commit.
2. **Backend lane:** the migration and RLS check, the main account service, IPC and unit tests,
   the `backend/README.md` section and the internals paragraph.
3. **UI lane:** the account store, the rail control, Settings → Account, and the privacy
   notice.
4. **Integration:** rebase both lanes onto `main`, write the changelog entry, run the E2E gate,
   then get the owner's eye approval.
