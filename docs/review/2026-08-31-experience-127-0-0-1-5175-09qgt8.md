# Experience review — Deck renderer at 127.0.0.1:5175

**STALE for release purposes.** `deploy_rev` equals `head_sha`, but the Vite dev server serves the
**working tree**, not the commit: 113 files are uncommitted, and this checkout is shared with
concurrent sessions that edit it live. The code walked is `ad03f16` plus an unpinned dirty tree.
This report cannot support a `SHIP` decision.

**Host caveat, applies to everything below.** Deck is an Electron/Tauri desktop app. `npm run dev`
serves the renderer with no host process, so every IPC call rejects and is caught. Findings are
tagged `REAL-UX` (would look the same in the packaged app) or `absent-host` (an artifact of the
missing bridge). Only `REAL-UX` findings are graded.

```yaml
severity:   high
confidence: high
class:      REAL-UX
evidence:   docs/review/assets/09qgt8/board-default-1440.png and board-more-menu-1-1440.png — two
            identical "…" buttons at x=1378 and x=1408, 6px apart, same glyph, same accessible name
            "More actions", same aria-haspopup="menu".
            Re-measured independently by the parent on a COLD page load (not just after the walk):
            one `.stage__strip-actions` inside `.stage__strip`, holding TWO sibling `.ftoolbar`
            elements; `.deck-frame` holds only `__lights` and `__spacer`; `.window` carries
            `window--sidebar`; `.tabbar` count is 0.
            Behavioural half: clicking the RIGHT button (x=1408) sets `aria-expanded="true"` on the
            LEFT one (x=1378) and anchors the menu there; the control actually pressed stays
            `aria-expanded="false"`. Reproduced twice with a verified-closed state in between.
impact:     Everyone, on every launch. `More` is the only entry point to Settings and every pane
            action. Sighted users get two indistinguishable triggers; screen-reader users hear the
            same name twice and are told the button they just pressed is collapsed while its menu
            is open.
action:     Render one feature toolbar in `.stage__strip-actions`, and make `moreOpen` per-instance
            so `aria-expanded` tracks the trigger that was pressed. Starting point: `chromeActions`
            (src/ui/app.tsx:1744) is a single JSX element object referenced at three render sites
            (src/ui/app.tsx:1982, :2031, :2108) — reusing one vnode across positions is the first
            thing to check. `DeckToolbar` (src/ui/toolbar/deck-toolbar.tsx:186) and `FeatureToolbar`
            (src/ui/toolbar/feature-toolbar.tsx:276) each emit exactly one `.ftoolbar`, so the
            duplication is at the mount level, not inside the component. That mechanism is a
            hypothesis the parent did NOT confirm; the two-instances measurement is confirmed.
```

HMR was ruled out as the cause, but with a stated limit: the console log contains no `[vite]` or
`hot updated` lines, the message counter held steady through the whole walk, and the cold-load
re-measurement above shows the duplicate on first paint. However, module URLs in the log carry six
distinct `?t=` transform stamps (e.g. `app.tsx?t=1788160562534`), so the dev server had re-transformed
modules for other sessions' edits before this run — a fresh page load of stamped modules is still a
clean mount, but the served source was not pinned.
